# ADR-0180: What a release promises

- **Status:** Proposed, 2026-10-11, at the author's direction ("go ahead and address all of them"): its checks are built; the promise binds from the release the author names 1.0.0 (decision 6).
- **Date:** 2026-10-11
- **Refined by:** ADR-0181 — a sandbox's controls and the tools' names promised too.
- **Refines:** ADR-0177 (an engine release's upgrade), ADR-0150 decision 2 (the wire), ADR-0116 (the flow format)
- **Relates to:** `guides/wire.md`; `design/flow-format.md`; `guides/integrate.md`; `guides/write-a-flow.md`; ADR-0179

## Context

A developer building an application on ObjectFlow depends on three things the engine gives them: the service's wire, which their application calls; the flow format, in which they write their rules and the examples that hold them; and their deployment's store, which holds their data. Nothing says today which of these a later release may change. The wire is `/v1` by name only; the flow format is "draft 2, adopted", and a description carries no version; the store is carried to a newer release by `upgrade` (ADR-0177), the one surface whose compatibility is held by a test. The second procurement integrator named the store's upgrade the first blocker for production, which ADR-0177 built; no reviewer has yet asked what a release may change on the wire or in the format, but an application's team plans every upgrade by that answer, and a developer deciding whether to build on the engine asks it first.

Industrial practice is settled for each surface. An HTTP API versions its path and, within a version, only adds: a new operation, an optional key, a field, never a removal or a change of meaning, so a client that ignores what it does not know keeps working (the compatibility rules Stripe and Kubernetes publish for their APIs). A language or a configuration format keeps every valid document valid within a major version, and a check that would now refuse one arrives first as a warning (Kubernetes's deprecation policy; a compiler's lints before errors). A release is numbered by semantic versioning, the major for a break of what it promises.

## Decision

1. **Three surfaces are promised**: the wire `/v1`, as `guides/wire.md` documents it, with what a deployment's automation and an application's evaluators are written against, the service's flags, `GET /health` and the evaluator endpoint's call and answer (ADR-0175 decision 4); the flow format, as `design/flow-format.md`, its schema and the examples format define it, and the flow checker's finding codes; and a deployment's store, as `upgrade` carries it. *Amended 2026-10-11 by ADR-0181 decision 6, which promises a sandbox's controls (`/sandbox/*`), since an application's tests of its time rules and evaluators run on them, and the generated tools' names; this said the controls were not promised.* **Nothing else is**: the core's Rust API, the reference runner's and the Flow Studio's, the text of a finding, a fault or a remedy's explanation, the plants, a `not_computed` list, which only shrinks, and every measured figure.
2. **Within `/v1` a release only adds**: an operation; an optional request key; an answer field; a verdict `kind`, an `invalid_input` reason or a finding code. It never removes or renames any of these, changes a field's type or meaning, makes an optional key required, changes a default such as a page's 100, or changes an operation's status codes. A client therefore **ignores answer fields it does not know, handles a refusal of a `kind` it does not know by its `remedy`**, of which there are five and no more, and sends only the keys the reference lists, since a service refuses others as `400`, which is how a client learns it has met an older service. A change that needs more is `/v2`, which a minor release may add beside `/v1`; only a major release stops serving `/v1`. The same rule holds `GET /health`'s fields and the evaluator endpoint's JSON; a flag of the service is added in a minor release and renamed or removed only in a major one.
3. **A description valid under a release stays valid, means the same, and its examples pass, under every later release of the same major version.** A release may add keys, constructs, expression functions, notices and finding codes. A check that would refuse a description it accepted before, a notice made fatal or a rule the checker newly enforces, arrives as a notice in a minor release and refuses only from the next major. Where an outcome contradicted `flow-format.md` or `declaration-syntax.md`, its correction is a fix, not a break: it may land in a minor release, named in the release's `changes`, since the document is the promise and not the defect.
4. **A description carries no format version.** Every description is of format 1, the format `flow-format.md` defines when the promise binds; a format 2, if one is ever needed, is declared by a key its descriptions carry, and the major release that adds it reads both.
5. **A store is upgraded from every earlier release of the same major version, and from the last of the major before it**, as ADR-0177 builds; a release is never downgraded, and its notes say to back the store up first.
6. **The engine release follows semantic versioning**: a major release for a break of a promised surface, a minor for an addition, a patch for a fix that changes no promised outcome. **The promise binds from 1.0.0**, which the author names once ADR-0174 to this one are reviewed and the third cold review finds nothing that would break; until then a 0.x release keeps these rules in intent, and a release that breaks one names the break in its `changes`.
7. **The promise is held by checks, not by care**:
   - **Format 1's corpus**: the design's sample modules and their examples as they stand when this decision is taken, copied to `design/flow-format/format-1/` with a digest of each file, never edited. `scripts/check-compat.py` checks that every file matches its digest, that each bundle checks with no fatal finding and that every example passes on the reference runner; `objectflow-core`'s `format_1` test, that each checks with no fatal finding on the core and that every example is run, as the core ran all 175 when the corpus was frozen. A release that needs the corpus edited breaks format 1.
   - **The wire's baseline**: `guides/wire-v1.json` lists each `/v1` operation, and each of a sandbox's controls, and the keys it takes. A test of the service (`v1_takes_what_it_promised`) fails where an operation or a key is gone, a break, and where one is added and not listed, so that every addition is promised deliberately.
   - **The store**: each release's fixtures, made by its own binary, are kept, and every later release upgrades and reads them alike (ADR-0177).

## Alternatives rejected

- **No promise until 1.0.0.** An application begun now would be written against nothing; the rules cost nothing to keep in intent, and the checks guard them from today.
- **A format version on every description**, Kubernetes's `apiVersion`: every description would carry a key that, until a format 2 exists, says nothing; its absence meaning format 1 for good costs nothing now and allows the key later.
- **A date-versioned wire**, Stripe's `Stripe-Version` header: it keeps every past behaviour of every operation alive behind a header, a cost a two-implementation engine cannot carry; a path version and additive changes within it are the cheaper practice.
- **Holding the format by the samples themselves**: the samples change as the format grows, an edit made with the change it accommodates, so a break would arrive with its own repair; only a copy no one edits shows one.
- **Promising the core's Rust API**: no application embeds it; an application's boundary is the wire, and a promise on the crate would freeze the engine's internals.

## Consequences

- `guides/wire.md` says what `/v1` promises and what a client does; `guides/integrate.md` and `guides/write-a-flow.md` say it in a paragraph each; `flow-format.md`'s status names format 1.
- `design/flow-format/format-1/` holds the frozen corpus, `scripts/check-compat.py` and `objectflow-core/tests/format_1.rs` check it, and `guides/wire-v1.json` the wire.
- Cutting 1.0.0 is the author's: a release entry in `objectflow-core::release`, its fixtures made by its binary, and this ADR accepted.
