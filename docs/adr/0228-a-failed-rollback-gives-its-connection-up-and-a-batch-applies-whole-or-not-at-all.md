# ADR-0228: A failed rollback gives its connection up, and a batch of requests applies whole or not at all

- **Status:** **Decided** 2026-10-23 under the author's direction ("go ahead with your recommendations"), after the review of issue #30.
- **Date:** 2026-10-23
- **Supersedes in part:** ADR-0037's rejection of an atomic batch (its "Alternatives rejected: An atomic batch") and its `batch` row, which described N independent requests and was never built
- **Refines:** ADR-0208 decision 4 (a group rolled back whole)
- **Relates to:** PRD F2 and C5; ADR-0019 (cascades), ADR-0023 decision 1 (one transaction per request), ADR-0104 and ADR-0105 (the engine takes no step of its own), ADR-0114 (who may do what is the upper layer's); `docs/research/atomic-batches.md`

## Context

**The constraint.** PRD F2 is a Must: governed state changes happen only through a declared transition whose rules pass, an override, a flow change's declared mapping or the erasure of a personal value, each recorded. `DESIGN.md` §5.1 says there is no ungated write. The author restated it while #30 was reviewed: the reason the engine sits below an application is that no object lands in an unexpected state under any condition, and that is never something that can be sacrificed. A fault in the engine's own handling of a rollback is such a condition.

**A failed rollback.** The review of #30 asked whether a rollback can be blocked. It cannot as a compensation can: it runs no transition and checks no rule, and work never committed does not count. Probed 2026-10-23 with a writer killed mid-transaction, SQLite in WAL mode with 11 MB of uncommitted frames on disk reopened holding only the committed row, and PostgreSQL 16.8 with a backend terminated holding 50,000 uncommitted inserts kept only the committed row. But the engine's code around the rollback could break F2. Eight rollbacks, in seven places, ignored their result, `Store::abort_group`'s among them. After one that failed, the connection could still hold the transaction it was to end. On SQLite the next begin fails, so nothing joins it. On PostgreSQL a begin inside an open transaction only warns: probed statement by statement, the next request's writes ran in the abandoned transaction and its commit committed the abandoned writes with its own, an ungated write. Read in its code, every failure of a rollback the PostgreSQL layer produces closes the connection (a lost connection, a statement past its deadline), so the hole was not reached, but no test held it shut.

**The batch.** Issue #30 asks for several requests on several objects applied together or not at all: a person reviews a set of changes and confirms them as one act, and a set of three that lands as two is not what was confirmed. ADR-0037 rejected an atomic batch because "it would let a caller compose multi-object transactions the declaration never described, which defeats the printable rule set". The issue's claims were each checked: no `/v1` operation takes more than one request; a transition's inputs cannot carry a list of requests; the language has no string operation; and a cascaded transition runs as the requesting actor (ADR-0019), so an effect cannot keep the upper layer's authorization of each request (ADR-0114). Record platforms let a caller compose an atomic set, bounded and idempotent; domain-driven design keeps a transaction to one aggregate, for reasons of concurrent transactions that one writer does not have; and work that waits on people or other systems is a saga, which no store transaction can hold (`docs/research/atomic-batches.md`, every source checked against its page).

## Decision

1. **A rollback that fails gives its connection up**, on both backends. Every rollback runs through `Connection::roll_back`. One that fails marks the connection discarded: no statement runs on it again, so no write joins the transaction it may hold and no read sees what that transaction never committed. On PostgreSQL its socket is closed at once, so the server ends the transaction rolled back.
2. **A begin on a connection whose transaction was never ended is refused**, on both backends, and gives the connection up. SQLite refused it already; PostgreSQL only warned. So F2 does not rest on how a rollback failed.
3. **A store whose connection was given up is not served on it again.** On PostgreSQL the next write opens the store again, as for a lost connection, and a read connection given up leaves its pool. On SQLite, where a failed rollback means a failing disk, the service latches the store, every read and write refused until a restart, with the code `store_connection_discarded` (`operate.md`), rather than open it again and hide the disk. Tested on both backends: a begin finding a transaction never ended, a transaction's rollback, its drop's and a savepoint's failing, and a group whose rollback fails, each leaving none of what it held. Each guard removed is caught by a test, on PostgreSQL too but for the one marking a discarded connection closed, which the closed socket already says there.
4. **`batch`**, the issue's `request_batch`, takes an `actor` and `principal`, as `request` does, and `requests`: each what `request` takes but those two. It may carry an `idempotency_key`.
5. **In order, in one store transaction, each judged as it would be alone**, against the state the requests before it left: its guards, every invariant of every object it writes, and its effect and cascades. Every state between the batch's requests satisfies every rule, as the states between requests sent one by one do, and none is ever seen by anyone else.
6. **All applied, or none.** The first request refused ends the batch: the answer names its index and its verdict, and the transaction is rolled back. What a refused request keeps is kept, and nothing more: the refused request's attempt row, naming the batch, and the sequence numbers every request of the batch drew, which are never reused (`flow-format.md` §4.12), written after the rollback. A batch that applies answers each request's verdict, in order. *(Corrected 2026-10-23: the row does not name the batch, which, rolled back, has no first event to name it by. It names the refused request's index in the batch, `batch_index`.)*
7. **Each request is recorded as if sent alone**, with its own transaction number and events, so history, subscriptions and metrics read it unchanged. Each event of a batch names the batch, by the position of the batch's first event, as a cascade's event names its cause, so a reader can see the requests were one act.
8. **Idempotent as the batch.** The same batch under the same key, from the same actor, answers its first outcome again, saying so; a different batch under it is refused `key_reused`, as `request` refuses one. *(Retracted 2026-10-23: "its first outcome" holds only for a batch that applied. A refused batch records no key, as a refused request records none, so sent again under it the batch is judged again. Held by `a_batchs_key_replays_it_whole_and_refuses_another_under_it`.)*
9. **Bounded**, refused `over_limit` past a number of requests set by measuring a batch's hold on the writer against C5, not taken from another platform. Derived from ADR-0208's measured phases, not measured as a batch: 100 requests would hold the writer about 320 ms. *(Measured 2026-10-23, the derivation overstated it: a batch flushes once, where ADR-0208's phases count a flush a request. 100 drafts held the writer 84 to 87 ms at p50. The bound is 50, as the Consequences record.)*
10. **What cannot be decided inside the transaction stays out.** A batch holding a change to the flow, a proposal, or a request that would consult an external evaluator is refused before anything runs. *(Retracted 2026-10-23: "before anything runs" is wrong for a request that would consult an evaluator. Whether it consults depends on the state the requests before it leave, which no check before the batch sees. The batch is refused at that request, every request before it rolled back, so none of it applies. Held by `a_batch_reaching_an_evaluator_applies_none_of_it`.)* The writer cannot be left mid-batch to ask an evaluator, and a flow change already takes the writer alone (ADR-0208 decision 3). The issue's case needs none of them.
11. **All or none, and nothing else.** There is no partial mode. A caller that wants requests applied independently sends them one by one; retries and sequencing over time stay the caller's.
12. **`check` takes a batch**, answering each request's verdict as the batch would leave the store, nothing written.
13. **It ships on integrity.** Before it is released, tested at each boundary on both backends: a refusal planted at every position leaves every object, event and interval as it was, row for row, beside the attempt and the draws decision 6 names; a kill and a store fault at every request and at the commit leave all or nothing after the restart; a panic at every request leaves nothing applied and the writer recovered; every committed batch passes the harness's checks; and mutants that commit after a refusal, or roll the draws back, are caught.

## Alternatives rejected

- **Keeping ADR-0037: the caller composes the set as an object of its flow**, a change set whose transition makes the changes by its effect. Every caller confirming a set would model it as a type, the set has no form to arrive in as inputs, the effect decides again what the caller decided, and its steps run as one actor, so the upper layer cannot authorize them one by one.
- **The caller compensates on a refusal.** Its undoes are new requests, refused by the same rules or failing with the store; they add to the append-only record what the partial act wrote and never remove it; and whoever read the partial state is not told (`docs/research/atomic-batches.md` §3).
- **Only transitions that cannot fail may be batched.** Almost no request in ObjectFlow cannot fail: an object may be gone, moved on or at another version, and the store may fail. A batch of requests that cannot fail needs no atomicity. Refusing what cannot be decided inside the transaction (decision 10) is the restriction that serves integrity.
- **A partial mode, as Salesforce's `allOrNone: false`.** A caller has it already, by sending requests one by one.
- **The batch's requests sharing one transaction number** as the record that they were one act. A transaction number is drawn for every write and keys the attempt log, so sharing one changes both; a field naming the batch changes neither.
- **Ignoring a failed rollback, as before**, since SQLite's next begin fails. F2 would rest on SQLite's refusal and on every PostgreSQL failure closing its connection, neither of which a test held.

## Consequences

- Decisions 1 to 3 are built, with their tests (`db.rs`, `request.rs`); `operate.md` lists `store_connection_discarded`.
- Decisions 4 to 13 are built: `request::batch` and `/v1/batch`, `request::check_batch` and `/v1/check_batch`, and the 0.6.0 store upgrade adding an event's `batch` and an attempt's `batch_index`. `wire-v1.json`, `wire.md`, `library-api.md`, `storage-schema.md` and `DESIGN.md` §10 say so. ADR-0037's `batch` row is superseded here.
- **The bound is 50 requests** (decision 9). Measured 2026-10-23 with `scripts/profile/batch-hold.py`, on a copy of the two-year profile store (`build-store.py`, 12,000 claims, 600 employees). The release build ran from the tree at `86d3200` with this record's later changes, on one idle i7-8700 with a Samsung 980 PRO. Each batch was of claim drafts. Alone, 50 held the writer 45 to 46 ms at p50 and 70 to 95 ms at p95 over 60 batches; 100 held it 84 to 87 ms at p50 and 114 to 138 ms at p95. Then single drafts were sent as they arrived for 60 s, with a full batch every second beside them. At the steady 50 a second, a single draft's p95 was 24 ms alone, 48 ms beside batches of 50, and 90 and 92 ms in two runs beside batches of 100. At the month-end peak of 100 a second, it was 45 ms alone, 74 ms beside batches of 50 and 124 ms beside batches of 100, past C5's 100 ms. A batch's own answer is not a request's, so C5 does not bound it: at 50 it took 103 ms at p95 at the steady rate and 129 ms at the peak. A batch of heavier requests, with cascades or invariants scanning a type, holds the writer longer per request than drafts do.
- **A batch's check takes the writer** (decision 12). It runs the batch and rolls it back, keeping no event, no number drawn and no attempt row, so its answer is exactly the batch's on the store as it stands. A request's check is lock-free and partial, and cannot be exact for a batch: the state a later request meets is what the earlier ones wrote, which a read connection cannot hold. On PostgreSQL its transaction is read-only, and on SQLite a write would take the writer's lock. It is gated by `reads_personal` as a request's check is (ADR-0206 decision 2), a target the store does not hold yet judged by every transition of its name.
- **Decision 13's tests**, on both backends: a refusal at each position (`a_batch_refused_at_any_position_leaves_the_store_as_it_was`); a store fault and a panic at each request and at the commit, in the core (`a_fault_or_a_panic_at_any_point_of_a_batch_keeps_none_of_it`) and through the service, with a kill at each, and one after the answer keeping all (`a_batch_killed_failing_or_panicking_at_any_point_keeps_all_or_none`). The faults are made by the core's `faults` feature, which no release build has. The adversarial harness's batched runs check every batch, applied or refused (`adversarial-harness.md`). Planted defects, each caught: a refused batch committed, its draws rolled back, a batch without its transaction, its events left unnamed, its refused row's index unset or the row dropped, a check that keeps or commits what it ran, and the check's personal gate removed or its judging of a target not held yet.
- The answers to the issue's questions: a later request does not name an object an earlier one creates until a case needs it, as JSON:API's `lid` allows, and the request's form can take one later; and a subscription delivers a batch's events as it delivers any, the field decision 7 names saying they were one act.
