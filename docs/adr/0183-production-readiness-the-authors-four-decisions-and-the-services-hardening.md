# ADR-0183: Production readiness: the author's four decisions, and the service's hardening

- **Status:** Decisions 1 to 4 **decided by the author**, 2026-10-11 ("go with your recommendations on the four questions", `design/production-review.md` §5). Decisions 5 to 10 built the same day under that direction, each fixing a finding of the review within the design; decision 7 rejects the review's recommendation, which the PRD forbids; decision 9's dependency approved by the author the same day ("approve the signal feature, go ahead").
- **Date:** 2026-10-11
- **Refines:** ADR-0174 decision 1 (a store is made only when asked), ADR-0114 (where the service's boundary is drawn)
- **Refined by:** ADR-0184 — the operator's retirement requested by nothing (decision 7's store acts); idle and half-sent connections closed, built (decision 10); ADR-0187 — a store's flow may declare who approves its versions (decision 7's store acts).; ADR-0188 — the store's volume in `/health` and `/metrics` (decision 8).
- **Builds:** `design/production-review.md` §4 and §5
- **Relates to:** `PRD.md` T6, N7, UC-15; `DESIGN.md` §10; ADR-0177 (the operator's upgrade); `guides/integrate.md` §2, §6, §9; `guides/wire.md`; `core/README.md`; `CHANGELOG.md`; `SECURITY.md`; `TODO.md`, "Production readiness"

## Context

The production review before 1.0.0 (`design/production-review.md`) found the engine not production-ready: four blockers, eleven majors and some minors, and four questions for the author. The author answered the four as recommended. This ADR records those answers and how each finding the review left to the engine was met, so that a later reader can weigh the choices again, together with what they rejected.

## Decision

1. **Release 1.0.0 is held** until the blockers and the majors are fixed and a second production review, on the same 36.7k-object store, finds none. ADR-0180's promise binds from 1.0.0, and it is worth more on a release that runs.
2. **CI runs every gate through one command.** `scripts/check-all` runs every gate the repository holds itself to: the core's format, clippy and tests, the Flow Studio's server and web app, every design check and the scenarios' replay on both backends. It runs each to its end and fails naming those that failed. `.github/workflows/check.yml` runs it on every push and pull request with `RUSTFLAGS="-D warnings"`, and checks the core's dependencies against the RustSec advisory database. Because CI and a change's check before its commit are one command, they cannot drift. A tag `v<version>` builds the service by `.github/workflows/release.yml`, which refuses a tag naming another version than the binary's and publishes the archive with its SHA-256 checksum. `CHANGELOG.md` and `SECURITY.md` state what each release changed and how a vulnerability is reported.
3. **A store is made only when asked.** A deployment's `--store` path that holds no store, absent or empty, is refused unless the start gives `--create`, so a mistyped path or a volume not mounted is never served as a new, empty store. `--create` on a path that holds a store opens it, so a first start's command is safe to repeat, but it belongs on the first start alone: a unit file that always gives it loses the protection. A store `--create` makes is `0600`, and SQLite gives its `-wal` and `-shm` the database file's mode. A store others can read is said at the start, never changed, since its mode is the deployment's.
4. **The engine still authenticates nobody, and the service may listen on a Unix socket.** `--socket <path>` listens on a Unix socket in an address's place, made `0660`, so the socket's owner and group are the only callers: the service's user and the application's, as a systemd unit's `RuntimeDirectory=` and `Group=` arrange. A socket a stopped service left is replaced, and a file of another kind never is. The boundary ADR-0114 leaves to the deployment becomes the file system's permissions, a check the kernel makes, rather than a convention about which addresses are reachable.
5. **`maintain` resolves its actor as a request does.** The review found an actor the store does not know pruning the attempt log. `maintain` now refuses an actor the store does not know as `actor_known` and one in a final state as `actor_active`, the refusal being its answer's `refused`, as its other refusals are. It reads no role and no kind. `DESIGN.md` §10 leaves who may maintain to the upper layer (ADR-0114), so the store validates the actor's identity and state, never a capability.
6. **A flag is a JSON boolean, and `inputs` an object.** `dry_run` on `publish`, `import_batch` and `upgrade`, and `propose` on `request`, take `true` or `false`, absent or `null` being false; anything else is `400`. `inputs` is an object or absent. The review's `"dry_run": "true"` was read as false and installed a version. A key of the wrong type is now refused as an unknown key is, never read as absent.
7. **What an agent may not do is the application's to refuse (F3).** Through the wire an agent drafted, submitted and approved a version, and retired the operator. The engine does not refuse an action by the requester's kind: PRD T6 says "no rule reads the kind of the actor making a request", N7 says the engine "evaluates no actor", and UC-15 has a person approve an agent's draft with "the upper layer deciding who may". So the guide (`integrate.md` §6) names the store's own acts an agent gateway must withhold: approving with `publish`, retiring the operator, `maintain`, `upgrade` and `import_batch`. The generated tools offer none of them, so an agent held to its tools cannot ask for them. A flow's own approvals are held by `taken_by` (ADR-0176, ADR-0182), the samples marking theirs (F2).
8. **What an operator needs is observable.**
   - The service writes one line on stderr for each answer, `<time> <method> <route> <status> <duration> ms`; a health check answering 200 and a scrape of the metrics are counted but not logged.
   - `GET /metrics` gives the answers by route and status, their seconds, the store's version and the clock's lead, in Prometheus's text format. It labels by the route matched, a path no route takes being `unrouted`, so a caller cannot grow the series.
   - `GET /health` opens the store's file afresh and reads its release, answering 500 where the store is gone or of another release. A pooled read connection would not do: its pages stay cached while no write moves the log.
   - `/health` also answers `clock_lead_seconds`, how far the store's clock leads the wall clock, which ADR-0174 decision 4 never moves back. The service says the lead at its start, and on each answer's line while there is one (CLOCK-PIN).
   - An evaluator's failure is logged by its function and its number of arguments, never their values or the endpoint's answer, which may hold personal data.
9. **The service stops gracefully.** On SIGTERM, as a supervisor stops it, or SIGINT, it takes no new connection, answers the requests in flight, and exits 0, saying when it began and when it stopped; a request still running after 30 s is cut and the service exits 1. The grace is longer than an import batch near the body limit took on the 36.7k-object store, 23 s, and shorter than systemd's default stop timeout, 90 s. A socket is removed as the service stops. Catching the signal in safe Rust takes tokio's `signal` feature, which adds two crates the lockfile did not hold: `signal-hook-registry` 1.4.8 and the `errno` 0.3.14 it depends on. The author approved the feature, asked about as adding one crate; the second was found when the lockfile was resolved, and is said here and in the report.
10. **Two minors are recorded and not built.**
    - **Idle and half-sent connections are not timed out.** `axum::serve` sets no timer on hyper's connections, so hyper's 30-second limit on reading a request's head never takes effect. Bounding it means serving connections through hyper directly, an accept loop of our own. Within the design's threat model a caller who holds connections open is the trusted application, so this waits for a release that needs it.
    - **The 2 MiB limit on a body is now documented, not configurable.** Measured on 2026-10-11, a body past it is refused `400`, `length limit exceeded`.

## Alternatives rejected

- **The engine refuses an agent's approval and its retiring the operator** (the review's recommendation for F3, which `TODO.md` carried). This was rejected because it is a rule reading the requester's kind, which T6 and N7 forbid and UC-15 assigns to the upper layer. Taking it would need a PRD revision, which only the author can approve, and it would still leave a buggy gateway able to act as a human. Withholding the acts in the gateway is the same protection at the layer the PRD names.
- **`maintain` the operator's alone, as `upgrade` is.** This was built first, at `TODO.md`'s recommendation, and withdrawn the same day: `DESIGN.md` §10 lists `maintain` among the acts whose permission is the upper layer's, withdrawing the built-in capabilities of ADR-0097, ADR-0105 and ADR-0112. `upgrade` stays the operator's by ADR-0177, a decision about an engine release rather than the flow's data.
- **`--create` refused on a path holding a store**, making it one-shot. This was rejected: a first start's script could not be run twice, and the protection is already lost by a unit file giving the flag every time.
- **Both a socket and an address at once.** This was rejected for now: one listener keeps one boundary to reason about, and a second process or a proxy can serve an address beside a socket.
- **A per-request timeout as a stand-in for idle timeouts.** This was rejected: it bounds a handler, not a connection that never finishes sending its head, which is what the review found.
- **Logging every health check.** This was rejected: a probe every few seconds would bury the answers an operator reads.

## Consequences

- Every deployment's first start needs `--create`, which `core/README.md`, `integrate.md` §2 and §9 and the deployment tests now give; a later start without it opens the store as before.
- The service's stderr carries a line for each answer, so a test or a supervisor reading it must drain it: the deployment tests do so in a thread, where a pipe left full would stop the service on its next line.
- `wire.md` gains `/metrics`, `clock_lead_seconds`, the body limit, the flags' type and `maintain`'s refusals. ADR-0180's promise holds `/metrics`' names as it holds `/health`'s fields.
- `SECURITY.md` names GitHub's private vulnerability reporting, which the repository's owner enables in its settings.
- A process that starts the service with its stderr piped must drain it: the Studio's server, its tests and the scenarios' replay read only the first line before, and the first full run of the gates after the log was added hung on a full pipe, so each now drains it, and `integrate.md` §9 says so.
