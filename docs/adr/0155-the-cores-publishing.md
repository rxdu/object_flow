# ADR-0155: The core's publishing, and its first slice

- **Status:** Accepted, 2026-10-05, by the author ("go with your recommendations on all four"), given four recommendations on how the Rust core takes on publishing: decisions 1 to 4. Decision 5, the first slice's scope, follows from them. Decision 6, and the revision of decision 3 it records, were made the same day while building the approval, under the same direction, and are open to the author's revision.
- **Date:** 2026-10-05
- **Refined by:** ADR-0156 — the core's checker: the checks run on the model, the schema validated by the core, examples run by the core, the Python checker the oracle, in four slices; the core computes no element version. ADR-0161 — an import from a module the version does not carry is fatal at publish.
- **Refines:** ADR-0153 decision 5 (the core does not check a module), ADR-0135 (the source's digest), ADR-0085, ADR-0097 and ADR-0147 (the `DeclarationChange` and its publish)
- **Relates to:** `design/publish-and-import.md` §1 to §3; `DESIGN.md` §9; `design/library-api.md` §6; `design/storage-schema.md` §5, §10; PRD F7, F10, F13

## Context

Every example passes against the core (ADR-0154), so what comes next is the design's, and publishing is the largest part of it that the core lacks. A publish checks the new source and runs its examples, compares it with the installed version, reads every object the change touches into an impact report, and, once approved, installs the version in one transaction around one migration event per object (`publish-and-import.md` §1).

Three facts shaped the recommendations:
- **Step 1 is the checks.** The sixty-four checks of `declaration-syntax.md` §10, the flow checker's contradiction analysis and the examples, about 5,900 lines of Python in `scripts/check-flows.py` and `scripts/check-syntax-doc.py`. ADR-0153 decision 5 kept the core from checking, deferring the checks to publishing.
- **The source's digest is SHA-256** (ADR-0135), which Rust's standard library lacks.
- **Nothing implements a publish's live part**, in Rust or Python, so no oracle compares it as the replay compared requests. The flow checker does compare a module with its previous version (`--previous`), statically.

## Decision

1. **A sandbox's publish trusts its caller's checks, and a deployment's waits for the core's.** In a sandbox, step 1 is the flow checker's, which the studio runs over a source before it reaches the core, as it does before `/sandbox/load` (ADR-0153 decision 5): the core loads the source with its strict loader, refusing one it cannot read as a fatal finding, and takes the checks and the examples as passed. Outside a sandbox, a dry run and a publish are not run, naming the publish checks, until the core has its own checker. Nothing unchecked is installed outside a sandbox. *Fulfilled 2026-10-05:* with ADR-0156's last slice the core runs every check and every example itself, in any store, so a deployment's dry run and publish run and a sandbox's no longer rest on its caller's checks; the flag that told a sandbox's store apart, which nothing else read, is gone. A sandbox's `load` still installs version 1 directly, its caller having checked the source (decision 4).
2. **The digest is computed with the `sha2` crate**, pinned in the workspace, over the source as ADR-0135 frames it, and held to `scripts/check-flows.py --digest` byte for byte.
3. **Publishing comes in slices.** The first is decision 5's. The second is the approval: the DDL around the mappings, one migration event per object, the admissions an `admit` records, the intervals of a newly tracked member, the redaction of a newly personal attribute, and superseding the other open changes and invalidating the proposals the change breaks. The core's own checker follows as slices of its own, held to the flow checker over every module of the design and every plant of its self-test, as the replay held requests to the reference runner, and with it every element's own version (ADR-0131). *Revised while building the approval:* this decision first put the elements' versions in the approval's slice; they moved to the checker's, since only the internal form the checks read carries one (`declaration-syntax.md` §1, check 22), and nothing the store records or the wire reports reads it. ADR-0156 then removed them from the core, which runs the checks on its model and computes no element version.
4. **A sandbox's `load` installs version 1 directly.** A sandbox is created at version 0, holding the built-in types, and its `load` installs the modules given as version 1, without a `DeclarationChange`, its source reference `sandbox:load` and its digest computed. Publishing then moves it on. This is the sandbox's shortcut PRD F13 allows; a deployment's store installs its first version by a published change (ADR-0126).
5. **What the first slice runs:**
   - `of_declaration` with versions 0 and 1, and every event and object carrying the version installed when it was written;
   - the built-in `DeclarationChange`, its states and transitions as `DESIGN.md` §9 gives them: `draft` and `revise`, taking the source as a map from each module's name to its description and from `<module>.examples` to its examples file, and `source_ref`, refused as `invalid_input` where it is empty, longer than 512 characters or holds a control character; `reopen`, `reject` and `withdraw`; `supersede`, only via a publish; and `submit` and `refresh`, which run the dry run, attach its report and are refused while it finds anything fatal, as `dry_run_clean`;
   - `publish` with `dry_run`, which produces the same report and writes nothing, and without it, not run until the approval's slice;
   - the dry run: the source loaded; compared with the installed version; every object of each type the change touches read into the impact report of `publish-and-import.md` §1 step 3, with each impact's severity from §2, the mappings of the source's `migration` applied in simulation and every invariant evaluated once after them, a violation no standing admission covers reported as a decision, covered or not by an `admit`;
   - the report as `PublishReport`, its `affected` ids per category; the fields the slice does not compute, such as compilation and fan-out, named as not computed on the wire.

6. **What building the approval found**, each settled by the design's nearest rule:
   - **A publish's redaction admits what it breaks** (D527). An attribute a version newly marks personal is redacted on every object already erased, by a `redact` event (`publish-and-import.md` §1 step 5), and that absence can violate an invariant that reads it, after the step that checks invariants has run. The `redact` event admits every invariant the absence leaves violated, as the erasure it completes would have (`declaration-syntax.md` §6.4).
   - **A type-changed attribute's intervals are set aside with its column** (D528). `storage-schema.md` §10 renames the column aside to `<name>__v<version>`, keeping its values readable, and was silent on a tracked attribute's intervals. They are set aside under the same name, the open one closed at the publish event, and the attribute of the new type opens its own, as any newly tracked member does.
   - **A draft's file is keyed by the name it declares**, a module's or `<module>.examples`, as decision 5 frames the source, and a file under another name is refused as `invalid_input` naming `source`, since the digest is computed over the names (ADR-0135) and would otherwise differ from `check-flows.py --digest` over the same files. The first slice did not check it.
   - **A version that would leave a personal value beyond erasure is not run.** Erasure reaches every value personal under any version an object's history was written under (ADR-0146 decision 2), and the core's erasure reaches what the installed version marks personal, which was the same thing while a store had one version. A publish can now drop, retype or unmark a personal attribute, after which an erasure would leave its values behind; until the core's erasure reads earlier versions, such a version's dry run and approval are not run, naming the attribute.

## Alternatives rejected

- **For decision 1:** porting the checker before any publish, which leaves the impact report, the part a person approves, unbuilt behind the longest piece of work; publishing without checks anywhere, which breaks "a publish either installs a version or installs nothing" (`publish-and-import.md` §1); a deployment's core calling the Python checker, which makes the engine depend on a second runtime, against ADR-0132.
- **For decision 2:** a hand-written SHA-256, about a hundred lines of hashing the project would own and test, to avoid a small dependency that does only this.
- **For decision 3:** the whole publish in one slice, which would be committed untested in parts no example reaches.
- **For decision 4:** every sandbox load going through a draft and a publish, which would run the dry run over an empty store on every load for nothing a person reads.
- **For decision 6:**
  - D527: refusing the publish where its redaction would break an invariant, which refuses the completion of an erasure the law does not leave open to refusal; leaving the violation unadmitted, an object then breaking an invariant with nothing recording why;
  - D528: leaving the intervals under the attribute's name, which reads the old values under the new type, an enumeration's member as a number; deleting them, which loses the history §10 keeps the column for;
  - the key: taking the module's name from the file and ignoring the key, which leaves two names for one file on the wire;
  - a personal value left behind: installing the version and leaving the gap to erasure's later slice, which would erase silently less than the law requires.
