# ADR-0229: A removed type's objects are moved into another type or retired on purpose

- **Status:** **Decided** 2026-10-24 under the author's direction ("go with your recommendations"), after the review of issue #31.
- **Date:** 2026-10-24
- **Superseded in part by:** ADR-0230 — decision 7's refusal of a moved or retired type that no module of the installed version declares, or one it holds retired: such an entry is a notice and moves nothing.
- **Refines:** ADR-0099 §7 (a removed type is retired), ADR-0027 decision 4 (a removal needs a mapping), ADR-0147 (the order a publish applies its mappings), ADR-0148 (an attribute whose type changed starts absent)
- **Relates to:** PRD F2 and F5 (revised in revision 26 to name a removed type); ADR-0018 and ADR-0226 (an object's id), ADR-0101 (no migration reaches an observation), ADR-0105 (a migration is F2's own route), ADR-0146 (one migration transition per object), ADR-0161 (a version carries every module it imports from), ADR-0163 (a type's name is unique across the store), ADR-0209 (an object's events folded give its row); `docs/research/moving-objects-between-types.md`

## Context

**The issue.** Issue #31, filed 2026-10-23, found that a version cannot carry a type's objects into another type. Renaming a type, splitting one into several or merging several into one leaves the old objects behind. The publish that drops a type holding live objects is accepted with no finding about them. Each claim was reproduced on 2026-10-24 at `67e3445`: `renamed_types` is refused `check:schema`; the publish without it reports only a `superseded` notice; the objects stay in their states under the retired type, and a transition on one answers `unknown_transition`.

**What the record decided.** ADR-0099 §7 retires a removed type: no object is created in it, no transition but its erasure applies, and its objects stay readable. It rejected no alternative that moves them. A removed state, by contrast, needs a mapping (ADR-0027 decision 4, `flow-format.md` §4.16), and so does a removed enumeration member that live rows hold (ADR-0099 §7). PRD F5 required the second and said nothing of a removed type, so a type's live objects could leave every rule without anyone deciding it.

**The constraint.** PRD F2: governed state changes only through a declared transition, an override, a flow change's declared mapping or an erasure, each recorded. A move is a flow change's declared mapping, so it is F2's own route (ADR-0105), and it carries F2's obligations: recorded on every object it changes, checked against every invariant, and applied whole or not at all.

**How platforms do it** (`docs/research/moving-objects-between-types.md`). ServiceNow, Camunda and Jira each re-type a record in place, keeping its identity, mapping its states, and refusing or losing data where nothing is mapped. An event store's split of one stream into two makes new identities, since one identity cannot name both halves.

**How the store holds an object.** Each type has its own table; the directory, `of_object`, records each object's id beside its type (`storage-schema.md` §2). The log, admissions, intervals, write index, external ids and legacy entries each name an object by its id, a key into the directory. An event names no type: a read by type joins the directory (`store.rs`, the event and interval reads). A stored reference's key names its target's table on SQLite, or the directory where the target has subtypes, and the directory on PostgreSQL (`storage-schema.md` §3).

## Decision

1. **A removed type holding an object not in a final state needs a decision.** The publish is refused, `removed_type:<Type>`, naming those objects, unless the version's `migration` moves the type (decision 2) or retires it on purpose. Retiring is written `retired_types: { <Type>: <reason> }`, the reason a sentence, as a migration's `description` is, kept in the version's source. A type retired, on purpose or holding only objects in a final state, is retired as ADR-0099 §7 decided, and the dry run names its objects in a notice, `retired:<Type>`. An observation kind is born final, so it never needs the decision. This refuses a publish 0.5.2 accepts.

2. **`migration.moved_types` moves a removed type's objects into types of the version.** For each removed type, a list of entries, each with:
   - `to`, a type the version declares, new or kept from the version before, so two types can merge into one that stays;
   - `where`, an optional condition on the old object; an entry without one MUST be its type's only entry;
   - `attributes`, optional, each target attribute and the expression that gives it;
   - `states`, optional, each old state and the target state its objects enter.

   A type named in `moved_types` or `retired_types` MUST be one the version before declared and this version does not, and none is named in both. Every object of the type, final ones included, meets exactly one entry: an object no `where` covers is fatal, `moved_type:<Type>`, and one two cover is fatal, `moved_type_twice:<Type>`. An attribute of the target is given by `attributes`, else carried from the old attribute of the same name and type, set or single alike, else absent, a required one left absent being fatal as for any mapping. A state is mapped by `states`, else carried to the target state of the same name; an object in a state with neither is fatal, `moved_state:<Type>.<STATE>`. A mapping into a superseding state is refused, as `removed_states` refuses one. `where` and `attributes` read what a backfill reads, the old object's own stored and derived attributes, `state`, the version's enumeration members and literals, never `now` or an input, with the version before the publish as their `declaration_version`. A value its attribute cannot hold refuses the publish, as a backfill's does.

3. **A moved object keeps its id.** Its directory row names the target, its row leaves the old type's table for the target's, and its version goes on from where it was. It takes one recorded migration transition, as every mapping's object does (ADR-0146): transition `migrate`, source `migrated`, the publish event as cause, the publishing actor, its `from_state` the old state and `to_state` the new. Its payload names the move, `moved: { from: <Type>, to: <Type> }`, beside its mappings. Its `wrote`, as every event's, holds what it changed, `null` for each old attribute the target does not take, so its events folded in order still give its row (ADR-0209). The move runs in the publish's transaction, so it is whole or not at all.

4. **What the move carries, and what it ends.**
   - Its standing admissions are discharged on the move's event: each admitted an invariant of the old type, and the target's invariant of the same name is another rule. Every invariant of the target is evaluated after all the mappings, and a violation is a decision, fixed, backfilled or admitted by an `admit` naming the target's invariant. Where both share a name, the move's event discharges the old admission before it records the new, and the discharge reaches only admissions recorded before it, so the new one stands.
   - Its state's interval is carried where the state keeps its name, and else closed and opened at the move's event. A tracked attribute's intervals are carried under its name where the target tracks it, and closed at the publish event where it does not, as for a member no longer tracked.
   - Its write index, external ids and erasure record are keyed by its id and stay. What was erased stays erased: a personal attribute of the target is left absent on an erased object, as a backfill skips one (ADR-0147). An erasure after the move judges each earlier event under the type the object was of then, read from the move's event, so what was personal before the move leaves the log too, a value the move left behind among it.
   - A value of a personal attribute that `attributes` or a carry would write into a non-personal attribute of the target is refused by the checker, as check 10 refuses a backfill's.
   - A pending proposal on a moved object is invalidated by the publish, since it was proposed under the old type's rules.

5. **A reference to a moved type keeps its values.** An attribute that referenced a moved type in the version before, and references in this version a type that each of its referents lands in or extends, is carried, not set aside as a type change (ADR-0148). Where a referent lands in a type the reference does not accept, the publish is refused, `moved_reference:<Type>.<attribute>`, naming the referring objects. On SQLite the reference's key names the target's table once the publish has rebuilt it.

6. **What does not move yet.** The checker refuses a move from or to any of these, naming why: an observation kind, since no migration reaches an observation (ADR-0101); a mirror, since only the import writes one (`flow-format.md` §4.15); an actor type, whose objects are the actors every event names; a type in a composition, one that declares a part or whose objects are parts, since a part's cascades and strandings follow its whole; an abstract type; a type with a superseding state, whose objects a supersession chain joins for erasure; a type observations are recorded against, since it declares their kinds; and two types of different `tracking`. Each returns when a case needs it.

7. **A move across modules needs nothing of its own.** A type's name is unique across the store (ADR-0163), so a type moved to another module under its own name is not removed, and keeps its objects and their transitions (probed at `67e3445`). An entry of `moved_types` sits in the module that declares its target, its `to` naming a type its module declares, so the checker can read what the target holds. It names a type the version before declared in any of its modules, and a publish refuses one that no module of the installed version declares, or one another module of the version still declares. *(Superseded in part by ADR-0230 decision 2, 2026-10-25: an entry naming a type no module of the installed version declares, or one it holds retired, is a notice and moves nothing; one another module still declares is refused, as before.)* The checker run on one module with `--previous` checks the old type against that file, and gives a notice where the type is not there, as it does for an import it cannot resolve. `retired_types` may sit in any module of the version.

8. **A moved object's history is the target's in every read.** Its events, intervals and admissions name it by its id, and a read by type reads each object's whole history under the type its directory row names. So a metric over the target counts what a moved object did before the move, under the transition and state names it did them by. The old type, which no version declares any more, has no metric to read. Every event stays as it was written, and the move's event names both types, so a reader of the history sees when the object changed type.

9. **Both implementations.** The core and the reference runner's publish (`scripts/flowpublish.py`), both checkers and the schema carry `moved_types` and `retired_types`, so each is the other's oracle (ADR-0166).

10. **The conditions it ships on**, each tested on SQLite and PostgreSQL: a rename; a split whose `where`s cover an object twice, or none; a merge into a new type and into a kept one; a state carried, mapped, and unmapped; a required attribute carried, given, and left absent; a reference carried, and one refused; an erased object moved, its personal values staying absent; a standing admission discharged and a target's violation admitted; a fault during the publish installing nothing; a moved object's events folded to its row, as the harness folds them; an erasure after the move reaching what the object held before it; and the refusal of decision 1. Planted defects that keep the old table's row, skip the directory, carry a reference to a type that cannot hold it, write an erased value, carry the old type's admissions, set a moved reference aside, or retire a live type without a decision, are each caught.

## Alternatives rejected

- **A new id, with a recorded link to the old object** (the issue's question 1). Every reference would have to be re-pointed, two objects would stand for one thing, and an erasure would have to follow the link. Platforms make new identities when one record becomes two; here a split partitions a type, each object reaching one target.
- **Retiring silently, as before.** A live object would leave every rule with nobody deciding it, where a removed state already needs a mapping.
- **A notice only** (the issue's third alternative). It makes the retirement visible and still leaves no way to carry the objects.
- **The upper layer re-creates the objects** (the issue's first alternative). The copies would have new ids and a history starting at the copy, every reference would need re-pointing, and the copy would be a script writing beside the engine, the second write path F2 rules out.
- **Keeping the old type's name forever** (the issue's second alternative). A type would mean something other than its name, which every reader of the flow pays for.
- **An entry only in the old type's module.** A module whose types all move elsewhere would be dropped, and could not say where its objects go, since a module declares at least one type.
- **Carrying the old type's admissions.** An admission admits one type's invariant; carrying it to the target's invariant of the same name would admit a violation nobody decided (ADR-0105).
- **A type recorded on every event, so a read by type reads each event under its type at the time.** The log and the interval index would each need a type on every row. A moved object's open state interval, entered under the old type, would then not count as the target's, so an ageing metric over the target would miss every moved object.
- **Moving actor types and composed types now.** An actor's moves reach every event naming it, and a part's its whole's cascades; neither case has asked for it, and each can be added when one does.

## Consequences

- PRD revision 26 widens F5 to a removed type: its objects are moved by a declared mapping or retired by a declared decision.
- `flow-format.md` §4.16, `flow-format-card.md`'s `migration` row and the flow format's schema gain `moved_types` and `retired_types`; `publish-and-import.md` §1, §2 and §3 the move, its findings and its order; `storage-schema.md` §10 the move's DDL and its retired row; `declaration-syntax.md` §6.6 the moved and retired type.
- The core's publish and install, its checker, the Python checker and the reference runner's publish change, with the tests of decision 10.
- `CHANGELOG.md` lists decision 1's refusal under its own heading, since it refuses what an earlier release accepted.
