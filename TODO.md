## Open model questions

- [ ] **Event ordering scope.** Decide whether the log guarantees global ordering across all objects or only per-object ordering. Global order means a serialized log and a throughput ceiling; per-object order is cheap and is usually what consumers actually need. "Events arrive in order" means very different things and should not be left implicit.
- [ ] **Retention versus slow consumers.** No-loss (ADR-0013) means an event a registered subscriber has not consumed cannot be pruned, so one dead subscriber pins the log indefinitely. Decide maximum retention, what happens when a subscriber falls too far behind, and whether that is an alert, an eviction, or backpressure.
- [ ] **Subscription granularity.** By object type, by specific transition, or by a filter over attributes. The first is trivial; the last requires the query engine and makes "which subscribers care about this event?" a per-event query.
- [ ] **Are subscriptions a built-in object type?** A subscription has durable state and a lifecycle (`active`, `lagging`, `dead-lettered`), which by this model makes it an object. Probably built-in rather than user-definable, so the recursion terminates — but decide it rather than inherit it.
- [ ] **Inspectable but unexecuted timing metadata.** ADR-0012 pushes timing rules ("escalate after four hours") into the automation layer, where they can drift from the object type they concern. Decide whether ObjectKeeper carries such rules as queryable declarations it never acts on — preserving one source of truth without a scheduler — or whether timing lives entirely upstairs. **Now load-bearing, not optional:** the first consumer has time-driven rules from day one (see Challenges, item 5).
- [ ] **State: stored or folded.** Given the event log of ADR-0013, decide whether current state is a stored column or a fold over events, and where provenance (actor, principal, source, `observed`/`inferred`/`asserted`, confidence) attaches. **`asserted` now has a concrete first use:** every imported object (ADR-0015). Whatever holds provenance must be able to say "asserted by the importer from legacy record X" and keep that distinct from a state a transition produced.
- [ ] **Read and query surface.** Undesigned, and now load-bearing rather than merely useful: ADR-0012 moves staleness detection upstairs, so the upper layer needs queries such as "which cases are in `awaiting_customer` and have not moved in four hours". Also covers what a query returns to an agent without exhausting its context, whether the read path can answer "which objects are blocked", and whether the query language is introspectable in the way guards are. The first consumer's available-to-promise computation (`wr:app/services/atp.py`) is a query of this kind — on-hand minus allocated plus un-pegged inbound, per model — and its operations design requires a single implementation that every surface calls.
- [ ] **Actors and authority.** Guards already reference actors and roles. Decide what an actor is, whether an agent carries its own identity plus a principal it acts for, whether delegation must attenuate authority, and whether a denied transition should produce a pending proposal rather than an error. **Observed shape in the first consumer, to start from:** a principal is a human (JWT) or an agent (API key bound to a user of role `AGENT`); effective permissions are role ∪ per-key allowlist, and the agent role's own set is empty (`wr:docs/DESIGN.md` §7.1); four roles and 41 permissions named `<RESOURCE>_<ACTION>` (`wr:app/models/enums.py`, `Permission`); a transition may carry `required_role` (`wr:app/core/state_transition.py:74-95`); an agent may create a Service but may not be its engineer-of-record (`wr:docs/agent-operations.md` §3); revoking a key is instant and per-key.
- [ ] **Schema evolution.** Decide what happens to objects already mid-lifecycle when a type gains a guard or an attribute: versioned types, eager migration, or forward-only requirements. **Same mechanism as import** (ADR-0015): the port is this situation for every object at once, so one design should serve both.
- [ ] **Global queries versus maintained projections.** Guards of the form "no other active Deployment on this Site" require scanning a type rather than traversing from an object. Decide whether that gets a real query path or is denormalised into maintained attributes — noting that a query is slow but truthful while a projection is fast and can silently lie. The first consumer chose "derived, not stored" for procurement demand (`wr:docs/proposals/operations-system-design.md` §9.0 rule 8) and a mirror for Xero contacts (its ADR-0003); both choices and their reasons are worth reading.
- [ ] **Action as a model element.** DESIGN.md now defines an action as a named, guarded, recorded operation that writes controlled attributes without changing lifecycle state (ADR-0006 needs it, or every controlled write forces a state change). Decide whether an action is a self-transition — from state S to state S, with inputs, guards and an outcome — or a distinct element. A self-transition is the smaller model; note that the first consumer treats a request to transition into the current state as a successful no-op and that this was flagged there as an audit hazard (`wr:TODO.md`, ST.6 findings), so a self-transition must be declared, never implied.
- [ ] **Approval.** Listed as in scope in DESIGN.md and never defined. Working reading: a guard of the form "a prior transition was performed by an actor holding authority X", reported with remedy class `delegable`. Decide whether that reading is right, and whether an approval is itself a recorded transition on the approved object or on a separate object.
- [ ] **Concurrency control.** Undocumented, and load-bearing for the first consumer (see Challenges, item 4). Decide: optimistic versioning per object, row locking inside the transition's transaction, or both; and how a conflict is reported — it is not a guard failure and must not be presented as one.
- [ ] **Deletion.** DESIGN.md never says what deletion is (see Challenges, item 6). The natural reading is a terminal transition gated on live references, remedy class `dependent`. Decide that, and decide how the first consumer's soft-deleted rows land on import — every legacy table carries `is_deleted` and those rows exist for audit.
- [ ] **External identifiers.** Objects need a stable identifier that other systems reference, distinct from the store's own id (ADR-0015). Decide whether it is a controlled attribute per type, a built-in field, or both, and whether uniqueness is an invariant.

## Challenges from the first consumer

Evidence from `~/RduWs/wr_inventory_management` that bears on accepted ADRs. None is resolved; each affected ADR carries a one-line pointer here. Recorded 2026-09-07.

1. [ ] **Atomic outcomes across references, not only parts.** Completing a Delivery moves each reserved unit to `SOLD` and creates its warranty contracts in the same transaction (`wr:app/core/state_registry.py:761-770`, side effects `_update_delivery_items_to_sold`, `_create_delivery_warranties`). Units outlive deliveries, so by ADR-0003's test they are references, not parts. The model describes composite-to-part cascades only (ADR-0004), and ADR-0007, ADR-0012 and ADR-0013 together route cross-object consequences to consumers through at-least-once events. That leaves a window in which a Delivery is `DELIVERED` and its units are still `RESERVED` — an inconsistent state of exactly the kind the project exists to prevent. Options not yet weighed: a transition that declares outcomes on referenced objects, each gated normally and committed atomically; a multi-object transaction primitive; or accepting the window and making it explicit in the declaration. Affects ADR-0004, 0007, 0012, 0013.
2. [ ] **Automatic transitions on the critical path.** The operations design's auto-fill: when a soft-pegged inbound unit reaches `AVAILABLE` at intake commit, its peg firms into `RESERVED` with no human step, specifically to close the double-booking window (`wr:docs/proposals/operations-system-design.md` §4 "Auto-fill on receipt", §5 step 5). Under ADR-0012 that becomes a consumer reacting to an event, which reopens the window. Whether this is a case of item 1 (an outcome declared on a referenced object) or a genuine trigger is the question. Affects ADR-0012.
3. [ ] **Derived views are used deliberately.** Slot state (`UNFILLED` / `FILLED` / `FULFILLED`) is computed from foreign keys and the bound unit's status and is "NOT persisted as a column" (`wr:app/models/enums.py`, `SlotState`); the operations design's single-path rules say "demand is derived, not stored" (§9.0 rule 8). ADR-0004 rejects derived *lifecycle* state, and rightly — but slots have no transitions of their own; they are a projection over Delivery items and units. Resolve by wording in ADR-0004: derived state that has transitions is rejected; derived read-only views are the query surface's business. Reopen only if slots turn out to need transitions. Affects ADR-0004.
4. [ ] **Concurrency is load-bearing and undocumented.** Double-booking was one of three motivating pains in the operations design (§1). The fix was a row lock on reservation and a `version` column on every entity with 409 on a stale write (`wr:docs/DESIGN.md` §2.6); the inventory ADR-0002 notes the TOCTOU hole a service-layer check leaves. ObjectKeeper's DESIGN.md never mentions concurrency control. Tracked as an open model question above.
5. [ ] **Time-driven transitions from day one.** `WarrantyContract` `ACTIVE → EXPIRED` on "contract expires" (`wr:docs/design/state-transition-system.md`); the alert catalogue lists low stock, procurement overdue, backorder aging, delivery date at risk, lease overdue and warranty expiring, all time-class (`wr:docs/proposals/operations-system-design.md` §6). ADR-0012 places these upstairs. The first consumer therefore needs a scheduler and the "inspectable but unexecuted timing metadata" answer at the same time as the core, not later. Affects ADR-0012.
6. [ ] **Deletion is a second lifecycle mechanism.** Every entity has `is_deleted` (`wr:docs/DESIGN.md` §7.3); a cascade registry deletes children, and its pre-delete hooks call `force_transition`, which bypasses guards (`wr:docs/design/state-transition-system.md`, "Integration with Cascade System"; `wr:app/core/state_transition.py:577`). The inventory ADR-0003 found that soft-deleting one redundant customer row would have cancelled 102 deliveries, 43 services and 120 warranty contracts. ObjectKeeper's docs never say what deletion is. A terminal transition gated on live references would have refused that cascade with remedy class `dependent`. Tracked as an open model question above.

## Data import

The port of the first consumer's production data is a designed path (ADR-0015, DESIGN.md "Data import"). Its properties were derived in discussion and are listed under Confirmations outstanding; the design work is here.

- [ ] **Override path.** Specify the authorised, recorded override transition that DESIGN.md's Known limits requires, such that import is its bulk use rather than a separate mechanism. Who may invoke it, what it records, and how it appears in history.
- [ ] **Validation report.** Specify what the importer evaluates per object (invariants, the structural guards of the creation transition, referential integrity) and the shape of the report. Decide the per-class disposition mechanism: clean upstream, or admit with a recorded flag that later transitions can see.
- [ ] **Legacy history.** Specify the read-only `legacy` history entry: payload, attachment to the object, and whether the read path presents it inline with ObjectKeeper's own history or separately.
- [ ] **Soft-deleted rows.** Decide the landing state for legacy rows with `is_deleted = true`, per type, once Deletion above is decided.
- [ ] **Files.** The first consumer stores photos (robot, delivery, service, intake), packing-list PDFs and label templates. ObjectKeeper does not store blobs. Decide whether objects hold references to files kept elsewhere and who migrates the files. Raised in ADR-0015, unanswered.
- [ ] **Cutover.** Big-bang or staged by object type with ObjectKeeper read-only for the remainder. A project-plan decision that the design must not preclude.

## Validation

- [ ] Choose a second case study that differs structurally from the first — specifically in **volume and object lifetime**, not just domain vocabulary. The first consumer is confirmed as the low-volume, long-lived, richly related kind: 279 live deliveries, 81 services, 203 warranty contracts and 123 live customers as of 2026-09-01 (inventory ADR-0003). That pulls the design toward deep composition and expensive cross-object guards. A high-volume, short-lived domain stresses query, indexing, throughput and retention instead. Designing against one alone produces an abstraction shaped like that one while claiming generality.
- [ ] Define the acceptance test as adversarial rather than happy-path: point an agent at the system and attempt to reach an invalid state. The weaker question — can it complete the workflow — does not test the objective. The threat model is mistakes, not malice (DESIGN.md), so the adversary is a fallible actor that guesses, retries and skips steps, trying every route; hostile actors with credentials are out of scope for this test.
- [ ] Establish that an object type's full rule set can be printed as a readable artifact for review by someone who knows the business process. Residual risk is specification gaps, which are only mitigated by legibility.

## Domain questions to answer from real workflows

These determine model scope. The first consumer's repository answers several; the rest remain open.

- [ ] **What proportion of needed guards are local to one object versus queries over related ones?** This decides how large the guard language must be. **Partial evidence:** of the guard predicates registered in `wr:app/core/state_registry.py` — `_is_admin_user`, `_no_unfilled_required_slots`, `_packages_instantiated`, `_delivery_ready_for_completion`, `_intake_ready` — all but the actor check read related objects (delivery items, slots, the packing checklist, intake items), not the object's own attributes. Heavily cross-object where observed. A count over the full operations design is still needed.
- [x] **Do type-level invariants occur in practice?** Yes. Two observed: one open engagement per unit, enforced by a partial unique index (inventory ADR-0002); exactly one active configuration version per SKU, enforced across three activation paths (`wr:docs/design/business-processes.md`). ADR-0009 stands; evidence attached to it.
- [x] **Does any axis exist that is genuinely 1:1 with an object for its whole life and has gated transitions of its own?** No. The inventory ADR-0002 found three orthogonal axes on a unit and resolved them as separate objects, not regions. ADR-0003 stands; evidence attached to it.
- [x] **Are there transitions where authority differs from capability?** Yes, and the list is short so far. Two observed: an agent may create a Service but may not be its engineer-of-record (`wr:docs/agent-operations.md` §3); cancelling a placed procurement order or reverting a committed intake needs `PROCUREMENT_CANCEL`, admin-only, because it undoes a committed obligation (`wr:app/models/enums.py`, `Permission`). A short list makes proposals an edge case pending the actor model.
